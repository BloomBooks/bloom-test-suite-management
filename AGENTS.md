# Workspace Notes

## Windows Shell Use

- Use PowerShell as the default command orchestrator in this workspace because the terminal tool is a persistent Windows PowerShell session.
- Do not use `node -e` for nontrivial inspection or transformation commands on Windows.
- Treat inline eval as unsafe when the command contains nested quotes, JSON literals, regexes, template strings, backslashes, or embedded file paths.
- For nontrivial ad hoc logic, prefer one of these instead:
  - a small `.mjs` file in the workspace
  - a small `.ps1` file in the workspace
  - an existing checked-in script
- Prefer the lowest-parser-count option. Avoid stacking JSON string parsing, PowerShell parsing, and JavaScript eval in one command.

## Repository layout

- **`import/`** — the one-and-done historical import (frozen). `prepare-import.mjs` + `import-to-notion.mjs`, with sources in `import/sources/`, hand-authored curation maps in `import/curation/`, and prepared output in `import/output/`. Data-model docs in `import/schema.md`.
- **`lib/notion.mjs`** — shared Notion plumbing (HTTP client + retry, page/database operations, rich-text/block helpers, incl. `linkifyRichText`). Both the import and the clone tool import from here. No top-level side effects.
- **`clone-test-suite-run/`** — the ongoing maintenance tool (clone the latest suite run into a new one). Scaffolding so far.
- **`assign-case-id/`** — source of record for the val.town webhook val that assigns the next `Test Case ID` to cards created directly in Notion. Deployed on val.town; self-contained (no `lib/notion.mjs`). See its README.
- **`notion-config.json`** (repo root) — shared `parentPageId` + live database id, read by both tools.

## Notion Import

- The model is a **single Notion database: `Test Case Runs`.** There is no separate `Test Cases` or `Test Suite Runs` database.
- Suite-run membership is a closed `Test Suite Run` **select tag** on each run card, not a relation.
- Each run card is the merge of the full test case definition and one run. The case summary is the card title; the rest of the durable case metadata (legacy number, dokimion id, priority, prior issues, est. time, areas, summary, original description) is folded onto each run card as its own properties; the parsed checklist steps/notes go in the page body as a to-do list. Each run card corresponds to exactly one execution, so there is no execution-entry list; any raw cell that didn't normalize cleanly (skip reason, unknown/`Future` tester, unparsable date) is kept in the `Run Notes` property (a per-run notes field, also for tester notes; not carried forward when a suite run is cloned).
- Suite-run names drop the `BetaInternal` qualifier, and only suite runs at or after version 5.5 are imported (`MIN_SUITE_RUN` in prepare-import.mjs).
- `Assignee` is a closed select mapped to a fixed name set (Andrew, Bharani, Hatton, Jeffrey, JohnT, Steve, Noel, Heather, Colin, Gordon; SteveMc -> Steve). Cells that don't match — skipped runs, `Future`, review comments, unknown names — leave it blank (raw value stays in the body). This describes the frozen import only; live, that select is now `Assignee - historical` and `Assignee` is a `people` property — see "Live Notion Schema" below.
- The run outcome is a single native `Status` property (`Not started` / `In Progress` / `Problems` / `Skipped` / `Done`), derived from skipped/ok/assignee/issueLinks in `deriveStatus()`. It replaces the old `OK` and `Skipped` checkboxes and is meant to drive a Kanban board view. A skip assignee yields `Skipped`. Those are the options the frozen import wrote; live there is also a `Retired` option, used for cards taken out of the suite — see "Live Notion Schema" below.
- `prepare-import.mjs` reads `area-mapping.json`, `title-mapping.json`, `step-overrides.json`, and `summaries.json` to derive areas, clean titles, checklist steps/notes, and the one-line `Summary` from the spreadsheet. `summaries.json` is keyed by `Import ID` and supplies hand-authored summaries that override the heuristic; `Obsolete` cases get a blank summary.
- Besides the main `Bloom Test Plan.csv`, the optional `Bloom Test Plan - temp Dokimion cases.csv` is appended (Test Case IDs continue past the main set; `Import Source Row Number` is `temp-dokimion-<row>`). Rows 507-567 and 592-608 have 6.3/6.4 run data that merges into those tags (its `notes` column renders under a `Notes` heading at the bottom of the page body); rows 609+ are YouTrack-only issues with no run data (one card each, named `<BL-id> - <description>`).
- `prepare-import.mjs` produces `test-case-runs.json` (the only Notion-bound file) plus `suite-run-tags.json`, and `import-to-notion.mjs` should mainly transport those prepared values to Notion.
- When updating existing run card bodies, use `IMPORT_REPLACE_BODY=1` so old body content is replaced instead of preserved.

## Live Notion Schema

- Clean slate: the new root page is `Bloom-Tests` (`37d4bb19df128097a7f9f7f0ab9f1a2f`). `import-to-notion.mjs` creates a fresh `Test Case Runs` database under `parentPageId` when `databases.testCaseRuns` is empty, and records the created id in `notion-state.json` as `databaseId`.
- Only the `Test Case Runs` database is written. The old `Test Cases` and `Test Suite Runs` databases are left untouched and are no longer in `notion-config.json`.
- In the `Test Case Runs` database:
  - `Test Suite Run` is a `select` (the closed suite-run tag list); option names cannot contain commas.
  - `Status` is a native `status` property (the single run outcome; replaces the old `OK`/`Skipped` checkboxes; drives the Kanban board). Live options are `Not started` (group To-do), `In Progress` and `Problems` (In progress), and `Retired`, `Done`, `Skipped` (Complete).
  - **`Retired` is the status for a card taken out of the suite — use it, not `Skipped`.** When a consolidation merges one card into another, or a card is dropped as obsolete, the retired card gets `Status` = `Retired`.
  - **`Skipped` is a deliberate scoping decision, not a shortfall.** It means the card is *still in the suite* but was consciously left out of this pass, because the team chose to narrow what this pass covers. It does not mean the testers ran out of time or failed to get to it. So: `Retired` = no longer part of the suite; `Skipped` = part of the suite, deliberately not run this time. Mixing them makes a run's results unreadable, because you can no longer tell which cards the suite has dropped from which it deliberately left out of scope. A large `Skipped` count in a pass is therefore a record of an intentional decision, and is not on its own evidence that anything is mis-prioritised or under-resourced. The August 2026 Talking Book / Publish: PDF / Blorg: Harvester cleanup set its retirements to `Skipped` because `Retired` did not exist yet; those have since been moved to `Retired`.
  - **A retired card must not carry forward into a new suite run, and the clone tool enforces that on two independent rules:** `Priority` = `Obsolete`/`Duplicate`, *or* `Status` = `Retired`. Either one alone keeps a card out; both rules stay in place. Before this was added, the tool filtered on priority only, so a card retired on the board but left at Priority 1/2/3 was cloned into the next run and — because the clone resets `Status` to `Not started` — came back looking completely live. Setting both markers is still the convention, but forgetting the priority is no longer silently destructive.
  - Whether the `Status` → `Assignee` automation below also fires for `Retired` is **unverified**: the cards observed on `Retired` kept their human assignee, but the person who moved them was also that assignee, so the two cases are indistinguishable. Check it before relying on either behaviour.
  - `Build Tested`, `Run Issues`, `Prior Issues`, `Legacy Number`, `Dokimion ID`, `Summary`, `Original Description`, `Run Notes`, `Import Source Row Number` are `rich_text` (`Dokimion ID` links to its bloom-test-cases file; `Import Source Row Number` is text because the temp-Dokimion source uses `temp-dokimion-<n>` ids). The case summary is the title, not a separate property. `Prior Issues` (formerly `Past Issues`) is issues found in earlier runs; `Run Issues` (formerly `Issue Links`) is issues found during this suite run — the clone tool merges the prior run's `Run Issues` into the new card's `Prior Issues` and blanks `Run Issues`.
  - The Notion API does not auto-linkify plain text, so `import-to-notion.mjs` runs readable content through `linkifyRichText()`, which makes bare `http(s)://` URLs and `BL-####` issue refs clickable. It is applied to the page-body Test Steps / Notes and the `Summary`, `Original Description`, `Prior Issues`, `Run Issues`, and `Run Notes` properties.
  - **Card body house style** (set August–September 2026; every card rewritten since follows it, and the earlier rewrites were re-shaped to match on 1 Sept 2026). Top to bottom: an optional standing-instruction paragraph (e.g. `N.B. Turn on Performance Measuring and monitor.` — the area notes say where it applies); the steps; an optional `Notes` heading with plain paragraphs for tester commentary, known issues and provenance. **No `Test Steps` heading** — the steps start directly. Earlier rewrites added one and Hatton is removing them by hand (September 2026); scripts must not add it, and cards that still have it are left for that pass rather than touched again. **Within the steps, only verifications are checkboxes.** An action that gets the tester somewhere (make a book, open a tab, click Upload) is a plain paragraph; the expected outcome that follows (“The dialog appears…”, “Confirm the thumbnail is…”) is a `to_do`. A step that combines an action with its check stays a checkbox. Long sequential cards read as prose interleaved with tick-boxes, not as a wall of boxes. Cross-card references are live Notion links labelled with the target card's title and id (`Adjust Timings and the Timings File (#519)`), never a bare `#519`. A screenshot of an expected result goes inline as an `image` block immediately after the checkbox that describes it, with no caption and no prose duplicating what the picture shows.
  - **When a card is merged into or retitled, its `Summary` (≤20 words), `Dokimion ID` and `Prior Issues` must change with it** — the body and title are not enough. A merge target absorbs the absorbed cards' Dokimion ids and BL refs; its Summary is rewritten to cover the whole card. This was missed twice in the 2026 cleanup (caught by audit both times), so treat it as part of the merge, not a follow-up.
  - `Assignee` is a **`people`** property (real Notion workspace users), not a select. The old closed select survives alongside it as `Assignee - historical`, holding the names the import mapped. Writing it takes a user id, not a name: `{ Assignee: { people: [{ object: "user", id: "<uuid>" }] } }`.
  - **A Notion automation owns `Assignee` whenever `Status` moves.** Moving a card to `In Progress` or `Skipped` sets `Assignee` to whoever made the change; moving it to `Not started` clears `Assignee`. Via the API "whoever made the change" is the **integration**, so any script that writes `Status` silently reassigns the card to the integration account (e.g. `test-management-access`). If a script needs a card to keep its human assignee, write `Status` first and then set `Assignee` back. This is also why the clone tool can leave `Assignee` blank for free: its `Status` → `Not started` clears it anyway.
  - **The automation is asynchronous, so restoring `Assignee` once is not enough.** It can fire *after* your restore lands and overwrite it. Observed on one card of ten in an August 2026 batch: the restore succeeded, the immediate read-back looked right, and a later read showed the integration as assignee. Re-read after a beat and re-apply until it sticks; a single confirming read straight after the write can pass and still be wrong.
  - `Areas` is a `multi_select`, and the live option names carry a group prefix that the imported names did not: `Toolbar: <tool>` (e.g. `Toolbar: Talking Book Tool`, `Toolbar: Canvas Tool`), `Publish: <target>` (e.g. `Publish: ePUB`, `Publish: Web`), and `Blorg: <area>` (e.g. `Blorg: Harvester`, `Blorg: BloomLibrary Uploads`). Areas added since the import include `Games`, `Subscription`, `Book Navigation`, `Bloom Reader`, `Publish: Apps` and `Blorg: Other`. Match on the live names, not on `import/output/areas.json`.
  - Properties added since the import, not written by either tool: `Automation Notes`, `Original Feature Implementation`, `Assignee - historical`.
  - `Priority` is a `select` (`1` / `2` / `3` / `Obsolete` / `Duplicate`; `Obsolete` was formerly `Ignore`, and `Obsolete`/`Duplicate` cards are excluded when a suite run is cloned), `Status` is a `status`; `Test Case ID`/`Est. Time (min)` are `number`; `Tested On` is `date`.
- `import-to-notion.mjs` reconciles the live `Test Case Runs` schema by default: it drops obsolete properties (`Test Case` relation, `Active`, and the `Import ID` / `Import Run ID` upsert keys), converts any leftover `Test Suite Run` relation into a `select`, and adds any missing required properties.
- This is a one-and-done import (fresh DB, no upsert): there is no live lookup by a Notion property. `notion-state.json` (keyed by `importRunId`) only exists so an interrupted run can resume.
- New cards created directly in Notion get their `Test Case ID` from a val.town webhook val (`assign-case-id/valtown-assign-case-id.ts` is the source of record; the running copy is deployed on val.town). It only fills *blank* IDs with live-max + 1, so duplicated and imported cards are never renumbered. Consequence: a future import must start its `testCaseId` sequence above the live Notion max, not the spreadsheet max. See `assign-case-id/README.md`.
